## Deployment order

The project has two Terraform roots: a **bootstrap** layer and the **application** layer. Deploy the bootstrap first, then the application. Within the application layer, Terraform resolves dependencies from resource references; you do **not** need to apply each AWS service separately.

### 1. Reconcile three configuration mismatches first

The current files do not line up for a first deployment:

1. **State bucket name:** `bootstrap/main.tf` creates a bucket with a generated suffix, but `terraform/backend.tf` names a fixed bucket, `agri-pipeline-tfstate-soakoto`. After bootstrapping, make the application backend use the bucket name printed by the bootstrap output. The fixed bucket will work only if it already exists and is the intended backend.
2. **Role name:** `bootstrap/github_oidc.tf` creates `agriculture-data-pipeline-github-actions-role`. Both GitHub workflows instead try to assume `soakoto-terraform-multi-env-github-actions-role`. Update the `role-to-assume` ARN in `terraform-ci.yml` and `terraform-deploy.yml` to the actual AWS account and bootstrap role.
3. **OIDC repository trust:** `bootstrap/github_oidc.tf` uses GitHub's immutable owner and repository IDs in the subject condition. Supply the IDs shown in the repository's **Settings → Actions → General → OpenID Connect** page as `TF_VAR_github_owner_id` and `TF_VAR_github_repository_id`; the trust remains restricted to this repository.

Also note: bootstrap has no remote backend configuration, so **its own Terraform state is local**. Preserve that state file; the S3 bucket it creates is configured as the *application* stack’s backend.

### 2. Bootstrap the persistent AWS resources

Prerequisites: Terraform, AWS CLI v2, and AWS credentials with permission to create the bootstrap resources. The project uses `us-east-1`. Bootstrap creates the state bucket, GitHub OIDC provider, GitHub Actions role, and deployment permissions in `bootstrap/main.tf`, `bootstrap/github_oidc.tf`, and `bootstrap/github_permissions.tf`.

```bash
aws sso login --profile my-aws
aws sts get-caller-identity --profile my-aws

cd aws-agriculture-data-pipeline/bootstrap
AWS_PROFILE=my-aws terraform init
AWS_PROFILE=my-aws terraform fmt -check
AWS_PROFILE=my-aws terraform validate
TF_VAR_github_owner_id=<OWNER_ID> \
TF_VAR_github_repository_id=<REPO_ID> \
AWS_PROFILE=my-aws terraform plan

TF_VAR_github_owner_id=<OWNER_ID> \
TF_VAR_github_repository_id=<REPO_ID> \
AWS_PROFILE=my-aws terraform apply

AWS_PROFILE=my-aws terraform output -raw terraform_state_bucket
```

Use that output to align `terraform/backend.tf` with the created bucket. If the bootstrap OIDC provider already exists in the account, resolve that before applying; Terraform currently declares a new provider.

### 3. Deploy the application infrastructure from the CLI

The application Terraform configuration requires `alert_email` from `terraform/variables.tf`. It packages the Python handlers from `src/` using Terraform’s `archive` provider; you do not need to build or upload Lambda ZIP files yourself. Provider and version requirements are in `terraform/providers.tf`.

```bash
cd ../terraform

export AWS_PROFILE=my-aws
export TF_VAR_alert_email='you@example.com'

terraform init -reconfigure
terraform fmt -check -recursive
terraform validate
terraform plan -out=tfplan
terraform apply tfplan
```

If Terraform detects existing state that needs transferring to the corrected backend, use `terraform init -migrate-state` instead of `-reconfigure` and review its migration prompt carefully. The repo’s README contains the local deployment outline in `README.md`.

### 4. Resource dependency sequence inside the application stack

| Order / branch | Resources and dependency |
|---|---|
| Foundation | Data S3 bucket and Athena-results S3 bucket. Their versioning, encryption, and public-access settings attach to their respective buckets. Defined in `terraform/s3.tf`. |
| Compute permissions | Lambda execution roles and policies depend on the data bucket for their S3 object permissions; basic logging policies attach to the roles. Defined in `terraform/iam.tf`. |
| Functions | Ingestion and transformation Lambdas depend on their IAM roles and the data bucket, and their code archives are generated from the Python handlers. Defined in `terraform/lambda.tf`. |
| Event triggers | S3 invokes the transformation Lambda only after its Lambda permission exists. The schedule’s IAM role/policy must be ready to invoke the ingestion Lambda before the EventBridge schedule can target it. Defined in `terraform/s3.tf` and `terraform/eventbridge.tf`. |
| Analytics | Glue database/table depend on the data bucket’s `processed/` location. Athena workgroup depends on the results bucket. These branches can deploy independently of the Lambda triggers. Defined in `terraform/glue.tf`, `terraform/athena.tf`, and `terraform/s3.tf`. |
| Monitoring | SNS topic/subscription and CloudWatch alarms; each alarm depends on its Lambda, and the alarm action depends on the SNS topic. Defined in `terraform/monitoring.tf`. |

Terraform’s references encode these dependencies, so a single `terraform apply` plans and orders them. Some independent branches may be created in parallel.

### 5. Configure GitHub Actions and deploy

In the GitHub repository:

- Set the repository secret **`TF_VAR_alert_email`**; both workflows pass it to Terraform.
- Ensure `TF_VAR_github_owner_id` and `TF_VAR_github_repository_id` match the immutable IDs shown in GitHub's OIDC settings before applying bootstrap changes.
- Update both workflow role ARNs to match the bootstrap-created role and AWS account.
- Keep the application backend bucket aligned with the bootstrap output.

Then use **Actions → Terraform CI** to run checks. `terraform-ci.yml` runs Python tests, Terraform formatting/validation, and a plan; it does **not** apply infrastructure. **Actions → Terraform Deploy → Run workflow** runs `terraform-deploy.yml`, which plans and applies. Both workflows require working OIDC trust and the corrected role ARN.

### 6. Verify the running pipeline

After deployment, get the bucket name with `terraform output -raw data_bucket_name`. Invoke the ingestion Lambda once or wait for its hourly EventBridge schedule; ingestion writes under `raw/`, which triggers transformation into `processed/`. Check both S3 prefixes, then query `agriculture_data.weather_observations` through the configured Athena workgroup. Confirm the SNS email subscription when AWS sends its confirmation email.

The CI Python tests use Python 3.12 and install `boto3`; the production Lambda runtime is also Python 3.12. The app Terraform root requires AWS provider 6.x and archive provider 2.7.x, while bootstrap also requires the random provider 3.x.
